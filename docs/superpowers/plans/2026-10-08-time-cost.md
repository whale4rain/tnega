## How it was measured

Same task as the earlier report, on an empty git repo: "Add count.mjs that
prints the word count of a file, a node:test test, and README usage."
DeepSeek `deepseek-v4-flash` through `https://api.deepseek.com/v1`, driven over
the HTTP API (`POST /api/projects`, `POST …/messages`, poll `GET …/:id` until
every agent is idle). Times come from the Session logs: `assistant/message`
`durationMs` (model), `tool/result` `durationMs` (tool), and the
`approval/review` meta event minus its `tool/call` (automatic review).

## Where a turn spends its time

1. **Model output dominates.** 70–86% of wall time is the model generating.
   DeepSeek streams ~250–300 tokens/s; 33–44% of output tokens are hidden
   reasoning. The slowest single steps are the ones that write whole files
   (8–15 s for 2–4k output tokens). Prompt caching is healthy (90–96%).
2. **Every shell call in a project thread waits on an LLM review.** In
   `workspace-write`, `shell` is not auto-allowed (`permissionGuard`,
   `packages/cli/src/permissions.ts`), so each call, sandboxed or escalated,
   is reviewed by `LlmApprovalReviewer`. Execution itself took 14–1072 ms;
   the review took 0.9–12.8 s. Before the fix, review was 17–37% of wall time
   (g/h: 7–14 s; c/d: 21–33 s).
3. **The review's reasoning has a long tail.** Replaying the 29 real shell
   reviews from these runs against DeepSeek: with reasoning, median 3.2 s, p90
   19.4 s, and 3 of 29 ran to the 4096-token cap (~20 s), which the reviewer
   reports as "invalid decision". In a project thread that then escalates to the
   coordinator, a full extra coordinator turn: run a lost 29.8 s on one
   `shell` call this way (20 s review + 10 s coordinator). Without reasoning:
   median 1.2 s, max 1.6 s, no runaways. Verdicts: all 29 allow (with
   reasoning: 25 allow, 3 cap-outs, 1 deny of a plain `node --test`). On 8
   hand-written risky commands (secret upload, `rm -rf ~`, force push, env to a
   raw IP, `npm install`, reading `~/.aws/credentials`, prompt injection with
   `chmod -R 777 /etc`) both modes gave the same verdict: deny, with `node --test`
   allowed.
4. **Coordinator dispatch latency.** Time from the user's message to the thread
   starting was 10–15 s: two quick exploration steps (list_dir/read_project,
   then read_file/glob, ~4 s) and one `spawn_thread` step that writes a
   2.5k-character brief (6–11 s, 750–1350 reasoning tokens).
5. **Mid-turn messages break DeepSeek's cache.** DeepSeek keeps the model's
   reasoning across tool sub-turns server side and drops it at the next `user`
   message. A coordinator message delivered into a running thread is a `user`
   message, so the next request re-reads the history uncached: in run a, 36k
   prompt tokens became 27k with only 7k cached. Verified directly: the same
   history plus a `user` note costs fewer prompt tokens and a lower cache hit;
   plus a `system` note keeps both. Time cost is small at this size (one
   uncached prefill); it grows with thread length.

## What changed

- `CompleteOptions.reasoning: 'off'` (new, per call). The OpenAI-compatible
  adapter sends `thinking: { type: 'disabled' }` only for DeepSeek's own API
  host; other routes ignore it, so third-party gateways (including the
  default opencode-go route) see no new parameter.
- `LlmApprovalReviewer` asks for `reasoning: 'off'`. Measured: review median
  1.8 s → 1.0 s on clean runs, max 5.2 s → 1.2 s, and no more ~20 s cap-outs
  that hand the call to the coordinator.

## Still open

- **Reviewing sandboxed shell calls at all.** Even at ~1 s, a thread pays it on
  every command. The sandbox only fences writes, so reads and network still
  justify a review; skipping it is a product decision, not a fix.
- **Mid-turn coordinator messages** could be delivered as a `system` note (or
  folded into the next tool result) to keep DeepSeek's cache and reasoning, but
  that changes the durable message role; needs care for Anthropic routes.
- **Reviews of parallel tool calls run one after another**; reviewing them
  concurrently would save a review per extra call.
- **Cloud container quirks** (not tnega bugs): no bubblewrap by default, and
  `NODE_USE_ENV_PROXY=1` needed for the server's `fetch` leaks into the shell,
  where its warning broke the thread's stderr tests in run a.
