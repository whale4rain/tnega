# Project 记忆、冲突与文件修改权调研

> 状态：当前
> 取代关系：无；补充现有 Project 调研，不取代现行设计
> 当前实现：[Blackboard](../../packages/project/blackboard/src/index.ts)、[Project Host](../../packages/cli/src/project-host.ts)、[Thread Provider](../../packages/project/thread-local/README.md)

日期：2026-10-09。代码基线：`f293745`。本文是调研与候选设计，不改变现行规范或实现，不涉及 CI、发布或运行监控。记忆专项来源与分析见 [配套调研](2026-10-09-project-memory-research.md)。

## 问题与候选方向

建议把三个问题分成三条可独立验收的链路：

1. 记忆：持久事件 → 候选条目 → 证据与冲突检查 → 生效版本 → 按需提供给 Thread。
2. 裁决：同主题候选 → 区分时间/范围/事实与决定 → 按规则处理或派调查 Thread → 有来源的决议 → 通知受影响工作。
3. 写入：明确负责人 → 获得执行范围 → 工具和进程边界执行约束 → 验证交付 → 安全移交修改权。

Coordinator 仍只协调。事实核查、冲突实验、合并和集成验证属于 Thread；Harness 负责确定性约束。不要增加一个包办所有工作的“超级协调者”。

## 当前实现的起点

- `packages/project/blackboard/src/index.ts` 已有版本、来源、历史与 `commitAll`；版本条件防止同记录覆盖，但不能判断不同 ID 的两段话是否矛盾。`decision` 已在种类中，尚不代表已经有完整裁决流程。
- `packages/project/tool-blackboard/src/index.ts` 的 `write_memory` 直接提交正文与标签；`read_project` 默认每类至多 20 条，不能将一次默认调用等同于读到了全部相关知识。写入来源目前不能仅靠 `author` 还原完整证据链。
- `packages/project/thread-local/src/index.ts` 用提示词要求读取记忆、保存持久事实和分开写入范围；这些行为未形成系统门禁。
- `packages/cli/src/project-host.ts` 将内置执行、搜索、Office、产物等绑定到同一 Workspace；Thread 身份目录不是隔离的工作目录。
- `packages/sandbox/fs-sandbox/README.md` 明确工具围栏与内核沙箱的区别；`packages/project/blackboard-local/README.md` 明确同一 journal 不支持多进程写锁。

## 一手资料与能支持的结论

| 来源 | 能支持什么 | 不能据此推断什么 |
| --- | --- | --- |
| [Anthropic 多 Agent 调研系统](https://www.anthropic.com/engineering/multi-agent-research-system) | 独立工作范围与轻量产物引用能减少重复和信息搬运；高依赖任务的并行收益受限 | 调研系统的性能数字不代表 Tnega 编程任务的收益 |
| [Claude Code agent teams](https://code.claude.com/docs/en/agent-teams) | 官方建议成员分开文件范围；任务认领使用文件锁 | 任务认领锁不等于业务文件写锁，更不等于所有 shell 写入受控 |
| [Git worktree](https://git-scm.com/docs/git-worktree) | 可建立多个工作目录，HEAD/index 等具有各自状态，共享仓库部分元数据 | worktree 不是安全沙箱；`worktree lock` 防管理目录清理，不锁业务文件 |
| [etcd concurrency API](https://etcd.io/docs/v3.6/dev-guide/api_concurrency_reference_v3/) | 锁与租约相关联，所有权键可在事务中校验 | 在 etcd 持有锁并不会自动约束本机文件写入 |
| [Kleppmann 原文：分布式锁](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html) | 租约过期后旧执行者仍可能写；fencing 必须由写入接收端校验单调令牌 | 普通文件系统和已启动的 shell 不会自动识别令牌 |

以下均是针对 Tnega 的建议，而非上述产品已经提供的统一方案。

## 发现一：记忆应当事件触发、候选与生效分开

保留显式写入入口，但让它进入同一条受控提交路径。增加持久事件触发的补充抽取：用户明确决定或纠正、验证完成的工作里程碑、Thread 交接；上下文压缩前可做增量补漏。不要每个工具调用都启动模型整理。

事件先落 Session/Box，再记录待处理工作与游标。后台整理如果需要模型，交给有界的知识整理 Thread；它没有文件写入和授权裁决能力，只能提出候选。队列重放不能重复生成同一候选；用事件身份和抽取器版本去重。已有来源事件恢复即可，无需复制完整对话。

最小条目字段：主题键、类型（事实/决定/约定）、适用范围、短正文、证据引用、状态、有效时间或版本范围、替代关系。既有 `FactRecord` 继续提供作者、提交版本和时间。主题键应允许别名和纠正，不能声称模型生成的键能完全识别同义条目。

- 显式用户决定：绑定真实用户来源，范围明确且无冲突时可直接生效。
- Thread 已验证发现：先成为候选；有可引用证据、不与生效记录冲突时按规则提升。
- 工具输出、网页、模型推测：是证据或假设，不能自己升级成用户指令。
- 临时进度和原始日志留在 Session/checklist；长内容进 Artifact，外部地址进 Resource。

“工具执行成功”只证明工具调用成功，不证明工具输出中的所有事实可靠。必须区分证据有效性检查与事实真伪核查。

权限等级和“用户决定”标签由可信消息来源与现有授权链导出，不能让提议 Agent 自填即生效。语义检测只能产生有漏报/误报的信号；低风险无已知冲突条目可自动提升，关键约束仍要求更严格证据或明确决定。用户约定不因时间过去自动失效；环境事实可按有效期或代码版本变为待复核。worktree 内发现先限制在该分支/commit，只有实际集成后才能声称属于共享基线。

读取端同样需要改：Run 开始提供与任务相关的生效条目和版本引用，调用工具可追溯全文；冲突条目显示争议，不静默选一条。用分页、主题过滤与相关性检索替代默认前 20 条的假设。重要变更通过 Box 通知实际依赖旧版本的 Thread，在下一安全边界重新评估；普通知识不广播给所有成员。记录本轮实际使用的记忆版本，避免恢复时悄悄换上下文。

## 发现二：裁决先判定是什么冲突

| 情况 | 建议动作 |
| --- | --- |
| 相同信息、不同表述 | 合并证据与别名，保留来源，不按重复票数增加可信度 |
| 不同时间、分支或环境 | 分开适用范围；保留历史，不当作互斥事实 |
| 用户明确修改先前决定 | 在确认同主题同范围后替代旧决定，保留原消息与变更原因 |
| Agent 观点与用户决定矛盾 | 不覆盖决定；若执行不可行，发请求说明证据和影响 |
| 两项客观证据冲突 | 建争议记录，派只读调查 Thread 复核，Coordinator 接收结果并协调 |
| 价值取舍或用户要求本身不明确 | 给用户精简选项，由用户决定 |

时间新、模型自信高、Agent 数量多，都不能单独作为事实裁决依据。权限授权单独处理：记忆中的“以前允许”不能成为新的高权限授权。

并发控制继续使用 CAS，但锁住的是“主题下的生效集合/裁决版本”，不能只分别检查两个候选 ID；否则两个并发候选都看不见对方。可在同一主题索引记录上条件提交，并用 `commitAll` 原子更新条目、替代关系和必要通知。实际方案需与现有 Box 的消息封装一起设计，避免提交成功后通知丢失。

争议不必暂停整个 Project。暂停依赖该决定的动作，允许无关 Thread 继续。记录谁依赖哪些记忆版本，裁决生效后定向通知。

## 发现三：文件负责人、执行权与整合权分开

负责人是长期分工，执行权是某次活动工作持有的范围，整合权是修改共享基线的资格。三者不应因为 Thread 的一次 `done` 或 `idle` 就一并消失；它可能还有后台 Job。

### 最小可用阶段：共享 Workspace 单写者

先允许多个只读 Thread 并行，一个写入 Thread 持有整个 Workspace 的写入资格。等待资格的 Thread 标记为依赖等待，收到可用通知才继续；不要让模型反复轮询抢锁。多范围细分以后再加。

资格应按规范化的物理 Workspace 标识管理，至少覆盖同一宿主内使用该目录的多个 Project；只按 projectId 锁会漏掉跨项目冲突。多个 CLI/Desktop 进程需要宿主级排他锁或统一代理，现有 Blackboard 的 CAS 不能替代进程间排他。

Harness 在实际调用处校验身份与当前资格，并传入执行边界。必须覆盖写文件、删除/重命名、Office 工具、shell、MCP/插件以及后台 Job；无法约束的写入能力不得宣称受保护。审批批准和 `bypass` 不应默默跳过协作所有权：若不支持可靠隔离，就显式降为单写者模式。

无租约资格时不启动有写入能力的进程。交还资格前等待/终止相关进程树和 Job，确认已经停止。租约到期只能触发撤销流程，不能立即把同一目录交给新写者。恢复时以新 epoch 作废旧句柄；不能确认旧写者退出时保持阻塞。单调令牌能保护受控 API 调用，但不能阻止已启动 shell 的 syscall。

### 第二阶段：Git 独立工作目录

对于确实需要并行写代码的任务，每个执行 Thread 使用独立 worktree/分支，并锁定起始 commit；完成后将提交与验证证据交给专门的集成 Thread。Coordinator 只安排合并顺序，不亲自运行 Git 或解决冲突。

worktree 解决工作文件和 index 相互踩踏，不能消灭语义冲突。集成 Thread 仍须校验变更是否符合任务范围，并基于最新目标 commit 合并和验证；更新共享分支使用期望旧 ref 的条件更新。用户未提交改动必须保留，不默认复制、提交或覆盖。

当前工具 cwd 是 Project 级常量，不能只改 shell.cwd 就称完成隔离：搜索、读写工具、Office、产物 path、Git 工具、沙箱根、浏览器文件访问和 UI 打开路径必须一致。共享记忆与产物存储仍归 Project，不能随着 worktree 复制出多套 Blackboard。

Git 元数据与引用有共享部分，危险的仓库级操作仍需交给受控集成路径；独立 worktree 本身不等于隔离另一位用户或 Agent 的分支。

### 非 Git 项目

保持共享目录单写者作为默认。确有独立输出时写 Thread 专属输出目录，交付物按 hash 发布；将产物放回用户原文件时由受控整合操作检查原内容 hash，发现用户已改则停下处理。多文件原子合并需要另行设计事务/回滚，不能把一次 rename 的原子性推广到整批文件。

### 不优先做

- 不引入 etcd 或分布式锁集群解决当前本机单宿主问题。
- 不一开始做任意 glob 的细粒度并发写锁；目录包含、大小写、junction、重命名和生成器副作用会大幅增加复杂度。
- 不把所有 shell 命令靠字符串推断为“只读”；应以执行能力和沙箱策略判断。
- 不让所有 Thread 相互投票决定事实，也不建立永久运行的通用记忆 Agent。

## 限制

本次未做实现或性能实验，不能承诺记忆召回率、语义判断准确率或吞吐收益。单写者方案先降低并发覆盖风险，不阻止用户或外部程序直接修改文件；租约撤销和所有写入工具覆盖仍需逐机制验证。涉及新字段、队列和线程工作目录的变更应先通过独立 ADR 确认，不能直接把本文视为已接受的架构决定。

## 结论：建议实施顺序与验收

1. **基础契约**：来源事件、主题与范围、候选/生效/争议/替代状态；明确 legacy 记忆仍可读，但不伪造其证据等级。补齐 Run 读取记忆版本的记录。
2. **最低文件保障，可独立并行推进**：共享 Workspace 单写者、受控执行入口、进程退出后移交。无法覆盖任意工具的路径需明确能力限制。
3. **记忆形成与传播**：增量持久队列、按里程碑提议、相关条目读取、定向通知。先结构化主题检索，再按实测召回需要决定是否加向量索引。
4. **语义争议流程**：自动识别范围差异和重复，冲突建档、调查 Thread、用户取舍；所有裁决可追溯。
5. **并行写能力**：确认串行写成为实际瓶颈后，增加 Git worktree 与集成 Thread；非 Git 保持较保守路径。

建议验收案例（本次仅提出，不运行测试）：

- 用户纠正后旧约定不再作为当前事实提供；两条不同 ID 的冲突记忆不能同时悄悄生效。
- 网页中的伪指令不会升级成用户决定；重复报告同一原始证据不增加证据数量。
- 已过期事实保留来源但触发重新验证；相关知识超过 20 条时仍能检索目标条目。
- 候选抽取崩溃重试不重复提交；裁决与通知的崩溃窗口可恢复。
- 失去资格的进程不能继续修改已交给他人的目录；跨 Project 的相同 Workspace 不能同时授予写权。
- 用户在 Agent 读取之后编辑文件，整合必须发现基线改变，不覆盖用户内容。
- Thread 报告 done 时仍有写入 Job，不得提前交出写权。

衡量效果：必要记忆漏记率、错误记忆生效率、纠正传播延迟、每次工作增加的 token/延迟、争议误报率、写入等待时间、覆盖事故数、集成冲突率。指标应由小规模真实任务基线决定阈值，不从其他产品的宣传数字推导。
