## 问题

已有的 durable Session 和 Blackboard 保证历史与版本可追溯，但不能保证模型一定记住有用结论，也不能判断两条不同 ID 的记忆是否互相矛盾。下一步需要回答：什么信息可以成为共享事实、什么时候形成、谁能改变、其他 Thread 何时知道，以及发现矛盾后还能依据什么继续工作。

## 证据与当前基线

### 仓库实际边界

- `write_memory` 当前写入 `{text, tags}`，带作者身份；同 ID 修改要求 `expected_version`。新增使用随机 ID，两个互相矛盾的新条目不会发生版本冲突。[工具实现](../../packages/project/tool-blackboard/src/index.ts)
- `FactRecord` 已具备 `source`、版本、创建/更新时间；`FactSource` 支持消息和 Session 事件 ID，但当前 `write_memory` 提交没有传入来源。这是可复用基础，尚不是完整证据链。[公共类型](../../packages/project/blackboard/src/index.ts)
- `decision` 已列入 FactKind，模型可读取；当前记忆工具仍将事实、决策、约定一起写成 `memory`。不能把已有 kind 当作已经完成的决策工作流。[公共类型](../../packages/project/blackboard/src/index.ts)、[工具实现](../../packages/project/tool-blackboard/src/index.ts)
- Coordinator 提示词要求保存用户决策、约定和后续需要的已验证事实，Thread 也能保存长期结论；何时写、是否重复以及是否已验证仍由模型判断。Coordinator 明确不能调查文件、执行、验证；缺证据应派给 Thread。[角色提示词](../../packages/project/thread-local/src/index.ts)
- Blackboard 提供事务提交与条件更新，但单 journal 只支持一个 Provider 写入。现有版本保护解决存储层并发，不能据此声称解决语义一致性。[Provider README](../../packages/project/blackboard-local/README.md)
- 普通会话还存在 Workspace `.tnega/MEMORY.md` 及压缩时 consolidation，不能把它与 Project Blackboard 误认成同一机制。后续必须明确两者的作用域和权威来源，避免两套记忆互相覆盖。[领域词汇](../../CONTEXT.md)、[普通会话组装](../../packages/cli/src/server.ts)

### 外部一手证据

| 来源 | 确认的做法或结论 | 对 Tnega 的意义与限制 |
| --- | --- | --- |
| [LangGraph Memory overview](https://docs.langchain.com/oss/python/concepts/memory) | 区分 Thread 内状态与跨 Thread 长期存储；支持运行路径内写入或后台写入。前者立即可见但增加延迟和模型负担，后者可批处理但存在更新滞后；集合式记忆还要处理过量新增和错误更新。 | 支持混合触发的取舍分析，没有给出自动裁决业务冲突的保证。 |
| [Zep/Graphiti 论文 §2.1、§2.2.3](https://arxiv.org/html/2501.13956v1) | 保留原始 episode 与派生事实关联；区分系统记录时间和事实有效时间；LLM 比较相关事实是否存在时间重叠矛盾，旧边失效但保留历史。该版本明确优先新信息。 | 可借鉴来源链与有效期；“更新的就对”不能原样用于用户约束或权限。论文结果不等于 Tnega 多 Agent 决策正确率。 |
| [LongMemEval 论文](https://arxiv.org/html/2410.10813v2) | 测试信息抽取、跨会话推理、时间推理、知识更新和拒答；实验指出只压缩成孤立事实可能丢失重要信息，按对话轮次保留内容有价值。 | 共享短记忆必须能返回原始证据；评价不能只看检索命中。其对话问答基准没有证明并发写权限或操作授权的正确性。 |
| [Letta Memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks) | 持久记忆块可设置 `read_only`，使 Agent 不能自行修改指定块。 | 说明可变经验与受保护约束可以有不同写权限；具体角色及审批规则仍需应用定义。 |
| [Anthropic Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | 区分压缩、结构化记事、多 Agent；建议保留轻量引用，按需加载完整材料。 | 适合沿用 Blackboard 索引、Artifact 完整材料、Session 原始轨迹，不必把所有历史复制进共享记忆。 |

上述文献没有给出一种经过证明、适用于任意项目的“自动语义真值裁决器”。以下为结合 Tnega 约束提出的设计建议，不是文献中的既成结论。

## 发现与建议

### 1. 明确记录的性质，而不是把所有内容都叫事实

建议最少区分：

| 性质 | 示例 | 可以由谁确认 |
| --- | --- | --- |
| 用户决策/约束 | “本轮不改 CI”“目标版本 v0.4.24” | 真实用户消息或明确交互；Agent 只能忠实登记来源 |
| 观察事实 | “在提交 abc 的 Windows 环境下该测试失败” | 执行 Thread 提供工具结果、版本与环境 |
| 项目约定 | “产物统一进入工作台” | 已有规范来源，或得到授权的决策者 |
| 假设/建议 | “失败可能由并发写入造成” | 可以记录为待验证候选，不能自动变成执行约束 |
| 运行状态 | “Thread A 正在等待审批” | 由 Thread/Box 状态维护，不写成长期记忆 |

用户控制的是目标、约束和授权；事实真伪由证据支持。这不是一个全局“用户 > 工具 > 模型”的排序：用户可以说“要求测试通过”，但这不构成“测试已通过”的证据；测试输出也不能推翻“本次不测试”的指令。

建议把来源身份与授权范围由宿主绑定，禁止模型用一个 `authority: user` 字段自行提升权限。记录“曾允许一次发布”也不应产生永久发布许可。权限决策继续走原有权限机制；记忆提供可追溯上下文，不替代授权。

### 2. 用混合触发，让重要约束及时生效，普通经验批量整理

不建议每条消息、每个工具结果都调用模型总结，也不建议只在压缩或 Thread 最终结束时才记忆。

| 触发 | 建议处理 | 生效边界 |
| --- | --- | --- |
| 用户明确要求记住、纠正约定、改变约束 | 立即持久保存原始消息；生成带原文来源的决策记录 | 后续相关派工/执行前可见；语义有歧义时先保留原文，不伪造确定结论 |
| Thread 获得经验证且其他工作需要的结论 | Thread 显式提交候选及证据 | 通过校验后成为可读事实；影响当前协作时另发约束变更消息 |
| Thread 完成、交接、重大纠正 | 调度一次有界的增量抽取，检查是否遗漏长期结论 | 从上次已处理游标开始；不是重读整个 Session |
| 压缩/归档/暂停 | 保存恢复执行需要的检查点，并处理遗漏候选 | 工作进度仍留 Thread 状态；不自动提升为项目约定 |
| 稳定闲置窗口 | 合并同源重复候选、检查过期证据 | 不让闲置整理成为关键约束生效的前置条件 |

“自动触发”应由确定性事件和持久待处理队列保证；“应记什么”的语义抽取仍可由模型完成。队列项用来源事件 ID 和抽取版本去重，成功提交后才推进游标；中断后能够恢复，避免一次模型失败永久漏记。

保持 Coordinator 只协调：它可以登记用户决策和分派整理任务，不能自己调查结论。需要模型批量抽取/复核时交给有界的整理 Thread，默认无文件修改和外部副作用权限；存储校验、幂等和事务由 Service 负责。首版可先保留显式写入，只在完成/纠正/交接触发补漏，后续用实际漏记率决定是否加更多后台调用。

### 3. 为记忆补足来源、范围与有效性

建议模型可提交语义内容，宿主补齐不可伪造元数据。概念字段可以是：

- `text`、`category`、`scope`：结论是什么，属于哪类，适用于哪一 Project/Thread、环境、文件或代码版本。
- `sources`：真实 message ID、Session event ID、artifact hash、规范文件及 revision；短引用用于快速核对，完整证据保留原处。
- `status`：`candidate`、`accepted`、`disputed`、`superseded`、`rejected`；来源仍在但已过期的观察可以保留历史。
- `recordedAt` 与 `validFrom/validTo`：何时写入、何时适用分开；允许未知有效期，不由模型随意编日期。
- `supersedes`、`conflictRefs`、`resolution`：替代关系、争议组、裁决原因与授权/验证来源。

对代码观察优先绑定 commit、文件 hash 或环境 fingerprint；这些依赖变了就变成“待重验”，比统一 7 天 TTL 更合理。用户决策可以长期有效，直到用户撤回或显式期限结束。短期外部资料可标 `reviewAfter`，过期表示不能直接据此行动，不表示自动删除。

第一版不必引入图数据库。现有 Blackboard 的记录、history 和 commitAll 可承载元数据与失效关系；先补可追溯性，再根据检索规模考虑索引。现有无来源的旧条目保留为 `legacy/unverified` 语义，不伪造来源，也不直接升级为受保护决策。

### 4. 分开解决版本竞争和语义矛盾

**版本竞争**仍走 CAS：读取旧版本、提交时校验、失败后重新比较。不能收到冲突后只替换版本号原样重试，因为那仍是在覆盖别人改动。

**语义检测**建议先缩小范围，再由模型判断：

1. 根据 Project、对象、关系、适用条件、时间区间找到相关候选；已知单值槽位可用稳定 key，例如某作用域的目标版本。
2. 分类为重复、补充、不同条件下都成立、明确替代、真正矛盾、不确定。语义相似度仅用于召回候选，不能直接决定冲突。
3. 同来源重复可以确定性去重；显式、有权的替代更新可以自动建立替代关系；真正矛盾或不确定进入争议记录。
4. 检测通过到提交之间还要验证读取集合。两个新 ID 的候选若分别与旧快照比较，都可能误以为没有矛盾。需要同槽位/主题的串行晋升，或读取集合版本校验后重判；不能只 CAS 各自候选记录。

模型抽取和推断保持在确定性事务外；提交服务只校验结构、来源身份、状态转移、授权规则和读取版本。不要让 Service 内偷偷运行一个有执行工具的协调 Agent。

### 5. 裁决遵循职责，不实行最后写入者获胜

| 矛盾 | 处理 |
| --- | --- |
| 同一结论的新表述 | 合并引用，保留原始证据，不增加重复事实 |
| 不同环境或历史时点 | 增加限定条件/有效区间；不误判为互相否定 |
| 新代码验证推翻旧代码观察 | 负责 Thread 给出新证据，旧事实标为历史/失效 |
| 两个 Thread 的观察互相矛盾 | Coordinator 指派一个验证 Thread 检查环境、来源和复现；证据不足保持争议 |
| Agent 建议与用户约束冲突 | 用户约束仍有效；建议不得提升为替代决策 |
| 两条用户指令看似冲突 | 同作用域、明确撤销/替代可以登记更新；范围或意图不清且影响行动时才问用户 |
| 技术方案取舍且已有授权范围 | Coordinator 路由给负责 Thread 提建议，并在授权范围内做协调决定；调查和验证由 Thread 执行 |

不投票、不平均“置信度”，也不因为三个 Agent 复述同一个来源就算三个独立证据。证据去重应保留共同来源关系。

争议只阻塞依赖该事实的行动，其他任务可继续。未解决的争议不把任何一方静默当成真；已有用户约束在有效撤回前仍是约束。用户界面应展示双方主张、证据、受影响 Thread、负责处理者以及当前执行影响，而不只是一个“记忆写入失败”提示。

### 6. 解决已保存但仍在用旧结论的问题

记忆形成还需要读取一致性。建议每次 Agent Run 的上下文记录其读取的 Blackboard 游标和具体记忆版本；与本任务相关的用户约束在启动前由宿主加载，普通事实仍可按需检索。

新约束、替代或争议出现时，通过 Box 向受影响 Thread 发送短变更通知：条目 ID、旧/新版本、含义变化和是否需要停止依赖动作。运行中的 Agent 在下个安全边界确认读取；不要将全量共享记忆广播到每个 Thread。对权限、文件归属等必须即时阻止的动作，还要在执行层检查，消息本身不能撤销已经开始的副作用。

下一次恢复 Thread 时，先核对其依赖记忆是否变更，保留仍然有效的部分，重新读取变化部分。暂停期间更新的约定不能仅依靠旧 Session 中的摘要覆盖过去。

## 成本、评估与限制

建议先比较三个策略：现有显式写、每轮抽取、显式写加事件补漏。用同一批真实 Project 轨迹比较记忆准确率、漏记率、每完成任务 token、关键约束可见延迟与额外模型调用数，不能只比较写入条数。

评价样例应覆盖：

- 用户说“不测试”只适用于本次发布，模型不能记成“永久禁用 CI”。
- 同一决策被重复转述，只形成一条当前记录及多条来源。
- 旧指令被明确撤回，所有依赖任务在下个安全边界采用新版本。
- 同时创建相反候选，不能都晋升为同槽位的当前真值。
- 测试在两个 OS 结果不同，保留条件差异。
- 用户希望测试通过，但实际失败，不能把愿望存为通过事实。
- 外部文档声称“允许发布”，不能写成用户授权。
- 证据不足时报告不知道；旧版本问题仍能查到历史答案。
- 崩溃重放、抽取失败、人工纠正与后台抽取竞争，不漏事件、不覆盖人工修改。

核心指标建议包括：来源可追溯比例、误晋升率、错误替代率、过期事实使用率、用户无意义裁决次数、相关变更送达时间。候选数量与召回率只是辅助指标。LongMemEval 的知识更新和拒答维度可借鉴，但必须另加 Project 的并发、权限和生命周期案例，不能直接套其问答分数。

本文没有实现或跑实验，无法承诺抽取准确率、固定阈值、延迟和成本。图数据库、多 Agent 投票、每轮反思都不应作为第一版默认依赖。论文与产品文档在不同模型/任务下的结果只能说明方案有参考价值，不能代替本仓库验证。

## 结论

优先落地顺序建议：

1. 补来源绑定、分类与作用域，严格区分用户决策、观察和假设；保留当前显式工具并统一写入校验。
2. 增加候选、争议、替代关系及安全晋升；先用明确语义槽位解决高价值冲突。
3. 在完成、纠正、交接后做增量补漏；让记忆变更进入相关 Thread 的可靠通知和恢复检查。
4. 用真实轨迹评估后，再增加检索索引、更多触发点或专门整理 Thread。

整体策略是“来源先保存，候选再提炼，按证据和权限晋升，按任务依赖同步”。Coordinator 负责把工作交给合适 Thread 和处理决策，实际抽取、调查和验证仍由 Thread 完成；一致性和权限边界由代码落实。
