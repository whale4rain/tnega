# docs 文档规范

本目录保存项目的架构决策、设计研究、实施状态、验证记录和故障修复记录。
文档不是代码事实的替代品；涉及当前行为时，必须以实现和对应包的 README 为准。每次阅读文档只阅读其元数据，如果不是需要获取历史过期文档可以忽略不用读取，且过期文档不用维护。

## 什么时候写文档

- 最重要的核心：非必要不写文档，只有有价值或需要记录时写文档！
- 新增或改变公共 API、事件、持久化格式、生命周期、权限边界或模块职责时，先写或更新对应 ADR。
- 需要比较外部项目、记录实验观察或分析当前差距时，写入 `research/`。
- 需要拆解尚未完成的跨文件工作时，写入 `superpowers/specs/` 和 `superpowers/plans/`；本规范不要求整理其中的历史文件。
- 完成 benchmark、端到端测试、发布验证或故障修复后，分别写入 `eval-results.md`、`test/` 或 `fix/`。
- 用户可见的安装、CLI、配置和当前能力变化，更新 `zh-CN.md`；英文用户文档更新根目录 `README.md`。
- 已有文档的事实、版本、状态或实现发生变化时，优先更新原文档并补充取代关系，不要另起一篇重复说明。

## 文档写在哪里

| 内容 | 位置 | 规范 |
| --- | --- | --- |
| 当前架构决策 | `docs/adr/` | 一项决策一个文件；保留历史正文，在顶部标明是否仍适用 |
| 调研、对照、审计 | `docs/research/` | 说明证据、基线、日期和结论；新的审计要明确取代旧审计 |
| 实施计划与设计草案 | `docs/superpowers/` | 仅作为工作材料；完成后标记状态，不作为当前实现的唯一依据 |
| 当前用户文档 | `docs/zh-CN.md`、根 `README.md` | 只描述用户需要知道的已实现行为 |
| 评测结果 | `docs/eval-results.md` | 保存口径、数据源、有效样本和限制；不要只在进度表中重复数字 |
| 测试或实验记录 | `docs/test/` | 记录命令、环境、结果和失败限制 |
| 故障与修复报告 | `docs/fix/` | 记录现象、根因、修复、验证和遗留项，评测以eval开头 |

## 标准结构

除 `docs/AGENT.md` 外，文档标题后统一使用以下元数据：

```md
> 状态：当前 | 进行中 | 历史记录 | 已取代 | 部分完成
> 取代关系：无 | 被谁取代 | 取代谁
> 当前实现：实现事实、包 README、测试记录或“仅历史记录”
```

字段要求：

- `状态` 只描述文档生命周期，不代表功能完成度；功能完成度应在正文或测试结果中说明。
- `取代关系` 必须写文件路径或明确写“无”。只要文档中的协议、版本或结论不再适用，就不能写“无”。
- `当前实现` 必须指向当前源码、包 README、ADR 或测试结果；历史报告写“仅历史记录”并给出替代文档。
- ADR 依次包含背景、决策、后果和验证；后续修订追加更新段，不覆盖历史决策。
- research 依次包含问题、证据/基线、发现、限制和结论；审计必须写明代码基线。
- test/fix 依次包含目的、环境或触发条件、命令/现象、结果和遗留项。
- 日期统一使用 `YYYY-MM-DD`；路径使用仓库相对路径，并优先链接到具体文件。

## 维护规则

- 当前实现只允许有一个主要事实来源：代码和包 README 优先，ADR 解释决策，其他文档引用它们。
- 不把完整架构说明复制到进度文档；进度文件只保留状态、摘要和链接。
- 版本升级时同步更新相关 ADR、包 README、用户文档和测试记录，并在旧文档顶部标注取代关系。
- 不删除历史文档来掩盖冲突：修正当前文档、标明旧文档状态，并保留可追溯链。
- `superpowers/` 内的计划和规范遵循其自身工作流；本文件只规定它们的归类和状态标记。
